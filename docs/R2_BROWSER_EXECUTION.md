## What R2 changes

R2 adds these database tables:

`agreements`

`commercial_transactions`

`transaction_parties`

`transaction_terms`

`transaction_line_items`

It also adds four fields to the existing `obligations` table so obligations can be explicitly `MONEY` or `NON_MONEY` and, when appropriate, linked to a commercial transaction.

The migration automatically maps every existing V1 `orders` row to exactly one R2 `commercial_transactions` row using `source_order_id`. Existing order/version records are not deleted or replaced.

## Step 3 — Apply the R2 database migration in Supabase

Use the Supabase SQL Editor connected to the actual R2 database project.

1. Open the correct Supabase project.
2. Open **SQL Editor**.
3. Create a new query.
4. Copy the complete contents of:
   `supabase/migrations/20260921000000_r2_commercial_transactions.sql`
5. Paste it into the SQL Editor.
6. Review the first line and confirm it is the R2 migration filename in the comment.
7. Click **Run**.
8. Wait for the SQL result to show successful execution.

Expected result: the query completes without an error.

### Immediately verify the new tables

Run this separate read-only query:

```sql
select table_name
from information_schema.tables
where table_schema = 'public'
  and table_name in (
    'agreements',
    'commercial_transactions',
    'transaction_parties',
    'transaction_terms',
    'transaction_line_items'
  )
order by table_name;
```

Expected result: five rows, one for each R2 table.

### Verify V1 order compatibility

Run:

```sql
select
  count(*) as v1_orders,
  count(ct.id) as mapped_transactions,
  count(*) filter (where ct.source_order_id = o.id) as correctly_linked
from public.orders o
left join public.commercial_transactions ct
  on ct.source_order_id = o.id;
```

Expected result: `mapped_transactions` and `correctly_linked` equal `v1_orders` for a database where all existing orders were eligible for the backfill. A clean database with zero orders will correctly show zero for all three counts.

### Verify tenant isolation is enabled

Run:

```sql
select relname, relrowsecurity
from pg_class
join pg_namespace n on n.oid = pg_class.relnamespace
where n.nspname = 'public'
  and relname in (
    'agreements',
    'commercial_transactions',
    'transaction_parties',
    'transaction_terms',
    'transaction_line_items'
  )
order by relname;
```

Expected result: all five rows have `relrowsecurity = true`.

## Step 5 — R2 release gate

R2 is not certified merely because the source code is committed.

The R2 gate requires all of these to be observed:

1. GitHub R2 CI is green.
2. Supabase R2 migration completed successfully.
3. The five R2 tables exist with RLS enabled.
4. Existing V1 orders remain present.
5. V1 orders have deterministic R2 compatibility links.
6. No later-release schema (reconciliation, ledger, treasury, settlement or API/SDK) was introduced by R2.
7. Vercel deployment succeeds.
8. The browser Transactions surface loads safely.
9. No R1 tag or R1 migration has been retargeted or edited.

Only after all evidence above is recorded should the R2 certification release/tag be created.

## Rollback

Application rollback: use the GitHub browser to revert the R2 application commit and allow Vercel to redeploy the prior revision.

Database rollback: do **not** delete the new R2 tables blindly. Treat the applied migration as persistent state and use a reviewed forward migration if a correction is required.
